# A2A / MCP Protocol Support

The AI assistant built into n9e is exposed publicly as a standard [A2A (Agent-to-Agent Protocol)](https://a2a-protocol.org/)
agent, so any A2A-compliant client (Claude, ADK, other agent orchestration platforms) can use n9e's agent capabilities
(querying alerts / events / metrics / resources, running diagnostics, inspecting dashboards, and so on). An MCP
(Model Context Protocol) Streamable HTTP entry point is provided alongside it for the MCP ecosystem.

The implementation reuses the existing `aiagent.Agent` core; there is no parallel implementation.

> This document describes the **server-side implementation** (module layout, execution flow, design trade-offs).
> If you only want to know how to configure it for third parties, see [a2a-integration.md](./a2a-integration.md).

## 1. Configuration

```toml
[HTTP.A2A]
# Disable = false       # default false = enabled
# DisableMCP = false    # default false = enabled
# BaseURL = ""          # optional; when empty it is inferred from the request Host + X-Forwarded-Proto
```

| Field | Type | Default | Description |
|---|---|---|---|
| Disable | bool | false | Closes every public A2A and MCP endpoint |
| DisableMCP | bool | false | Closes only the MCP entry point; A2A is unaffected |
| BaseURL | string | "" | The absolute URL exposed in the AgentCard; when empty it is inferred per request |

The configuration struct is defined as `A2AConfig` in `pkg/httpx/httpx.go`.

Prerequisite: A2A / MCP authentication reuses `[HTTP.TokenAuth]`, which must be enabled.
If `HTTP.A2A` is not disabled while `HTTP.TokenAuth` is not enabled, a warning is printed at startup noting
that every `/a2a/*` and `/mcp/*` request will be rejected.

## 2. Public endpoints

| Endpoint | Auth | Description |
|---|---|---|
| `GET /.well-known/agent-card.json` | None | Public A2A AgentCard discovery (the v0.3+ spec path) |
| `GET /.well-known/agent.json` | None | The same, as a compatibility alias for older clients |
| `ANY /a2a` `/a2a/*` | `X-User-Token` | A2A REST + JSON endpoints (including the SSE stream) |
| `ANY /mcp` `/mcp/*` | `X-User-Token` | MCP Streamable HTTP, stateless mode |

Authentication fully reuses n9e's existing `tokenAuth()` middleware and behaves the same as for `/api/n9e/*`.
It is declared in the AgentCard via `securitySchemes` (`securitySchemeName = "x-user-token"`):

```json
{
  "securitySchemes": {
    "x-user-token": { "type": "apiKey", "in": "header", "name": "X-User-Token" }
  },
  "security": [{ "x-user-token": [] }]
}
```

The `name` value comes from `HTTP.TokenAuth.HeaderUserTokenKey` (default `X-User-Token`).

The AgentCard also declares:
- `Capabilities.Streaming = true`
- a single `n9e-assistant` skill, with a handful of English example prompts
- `DefaultInputModes` / `DefaultOutputModes`, both `text`

## 3. Concept mapping

| A2A | n9e |
|---|---|
| `ContextID` | `assistant_chat.chat_id` (ignored, and a new chat allocated, if it does not exist or does not belong to the caller) |
| `TaskID` | Generated by the SDK; bound to `(chat_id, seq_id)` through `Task.Metadata` when persisted |
| `Message.Parts[*].Text` | Concatenated into `MessageQuery.Content` |
| `Metadata.lang` | Forces the LLM's output language |
| `Metadata.page` | `AssistantPageInfo.Page` (only used when creating a new chat) |
| `TaskStatusUpdateEvent` | submitted / working / completed / failed / canceled |
| `TaskArtifactUpdateEvent` | The text stream (reasoning + answer), bridged from `aiagent.StreamMessage` |
| `Cancel` | `CancelAssistantMessageInternal` (cancel ctx + mark + finish stream) |

`Task.Metadata` uses two reserved keys to bind the SDK-generated TaskID back to n9e entities, so that Cancel can
locate the right one precisely:

| Key | Type | Description |
|---|---|---|
| `n9e.chat_id` | string | Corresponds to `assistant_chat.chat_id` |
| `n9e.seq_id`  | int64  | Corresponds to `assistant_message.seq_id` |

## 4. Module layout

```
aiagent/a2a/
  agent_card.go          # AgentCard construction + securitySchemes declaration
  handler.go             # NewHTTPHandler: assembles the a2asrv RequestHandler / RESTHandler
  executor.go            # a2asrv.AgentExecutor implementation (Execute / Cancel / heartbeat / terminalState)
  bridge.go              # StreamMessage → a2a.Event conversion (content/reason/step)
  user_ctx.go            # WithUser / UserFromContext
  mcp.go                 # MCP Streamable HTTP server (single n9e_assistant tool)
  executor_test.go       # end-to-end fake-backend unit tests
  taskstore/
    redis_store.go       # Redis implementation of a2asrv/taskstore.Store (Lua CAS)
    redis_store_test.go

center/router/
  router_a2a.go                  # configRegisterA2A: route mounting + a2aBackend adapter + middleware
  router_ai_assistant.go         # the existing HTTP entry point, reusing the shared internal logic
  router_ai_assistant_internal.go # shared exported symbols: EnsureAssistantChat / StartAssistantMessage /
                                  # CancelAssistantMessageInternal / clearWriteDeadline /
                                  # ErrMessageNotInflight and others

cmd/a2a-cli/
  main.go                # terminal test client built on the official a2a-go SDK
```

`aiagent/a2a` is decoupled from `center/router` through the `AssistantBackend` interface — the former never imports
gin or the router package directly, and the latter turns `*Router` into the interface with an `a2aBackend` adapter.

```go
type AssistantBackend interface {
    EnsureAssistantChat(userID int64, chatID string, page AssistantPageInfo) (*AssistantChat, error)
    StartAssistantMessage(userID int64, chat *AssistantChat, query AssistantMessageQuery, lang string) (*MessageStartResult, int, error)
    CancelAssistantMessage(ctx context.Context, chatID string, seqID int64) error
    CheckChatOwner(chatID string, userID int64) error
    StreamBus() aiagent.StreamBus
    MessageSnapshot(ctx context.Context, chatID string, seqID int64) (*AssistantMessage, error)
}
```

## 5. Executor flow

Middleware chain: `tokenAuth` → `user` → `injectA2AUser` → `streamingDeadline`.
`injectA2AUser` injects `*models.User` into `request.Context`; `streamingDeadline` clears the default 40 s write
timeout via `http.NewResponseController.SetWriteDeadline(zero)`, without which a long ReAct stream would hit
`i/o timeout` partway through.

`Execute()`:

1. Takes the user from ctx, and checks that `Message` is non-empty and that the concatenated part text is non-empty
2. Parses `Metadata.page` / `Metadata.lang`
3. `EnsureAssistantChat`: the supplied `ContextID` is reused only if it belongs to the current user; otherwise a new
   UUID is always allocated and a new chat created (preventing ID squatting and cross-tenant existence probing)
4. `StartAssistantMessage`: takes the ChatLock, allocates a seqID, writes `assistant_message`, initializes the
   streamBus, and starts a goroutine running `processAssistantMessage`
5. `yield`:
   - `NewSubmittedTask`, writing `n9e.chat_id` / `n9e.seq_id` into `Metadata`
   - `NewStatusUpdateEvent(working, nil)`
   - enters the streamBus forwarding loop
6. On termination it calls `terminalState()`, reading the `MsgStateGet` snapshot:
   - `ErrCode == MessageStatusCancel` → `Canceled`
   - `ErrCode != 0` → `Failed`
   - anything else (including a snapshot whose TTL has expired) → `Completed`
7. `bridge.Finalize(state, errMsg)` emits the terminal status update

`Cancel()`:

1. Takes `(chat_id, seq_id)` out of `ec.StoredTask.Metadata`; missing or malformed → `ErrTaskNotFound`
2. If `ec.ContextID` is non-empty and does not match `chat_id` → `ErrTaskNotFound` (anti-probing)
3. `CheckChatOwner` failure → `ErrTaskNotFound` (without distinguishing "does not exist" from "not yours")
4. `CancelAssistantMessage`: if the layer below returns `ErrMessageNotInflight` it is also mapped to
   `ErrTaskNotFound`; other errors are reported back as a `Failed` status update
5. On success it yields `NewStatusUpdateEvent(canceled, nil)`

### Bridge state machine

The three phases of `aiagent.StreamMessage` (`StreamMessage.P`):

| StreamMessage.P | A2A Event |
|---|---|
| `content` | The first one is `NewArtifactEvent(NewTextPart(delta))`, recording the artifactID; subsequent ones are `NewArtifactUpdateEvent` with the same ID |
| `reason`  | The same, except every `TextPart` is annotated with `SetMeta("adk_thought", true)` (ADK clients recognize it as a "chain of thought") |
| `step`    | `NewStatusUpdateEvent(working, NewMessage(role=agent, NewTextPart(stepText)))`; it also clears reasoningArtifactID so the next stretch of reasoning starts a new artifact |

A separate `LastChunk` artifact update is deliberately **not** emitted on termination: the a2a-go SDK's
`taskupdate.Manager` rejects an ArtifactUpdate with empty Parts (`ErrInvalidAgentResponse "artifact cannot be empty"`),
which would incorrectly flip the task to `failed`. In the SDK, the terminal status update is itself the end-of-stream
signal, and once a client sees the terminal state with no further deltas it treats the artifact as complete.

### Heartbeat

`heartbeatInterval = 30s` (see `executor.go`). It is selected on in the same goroutine as the stream: when no real
event has occurred for 30 s, an empty `NewStatusUpdateEvent(working, nil)` is sent to work around the default 60 s
idle timeout of nginx / ALB. Every real event calls `ticker.Reset`, so the heartbeat only fires when things are
genuinely idle.

A second goroutine is not used because the `yield` of an `iter.Seq2` may not be called concurrently.

## 6. TaskStore

The implementation lives in `aiagent/a2a/taskstore/redis_store.go` and is installed via
`a2asrv.NewHandler(WithTaskStore(...))`, so that `tasks/get` and `tasks/resubscribe` can retrieve task state across
process restarts and across instances behind a load balancer.

- Redis keys (24 h TTL, aligned with the streamBus):
  - `a2a:task:<taskID>` (Hash) — task JSON + version + user + context_id + updated
  - `tasks/list` is not implemented, so no per-user or per-context secondary index is maintained
- Updates go through a Lua CAS: check `prev_version` → on a match, atomically HSET, bump the version, and refresh the TTL
- Multiple instances: all center instances share the same Redis, and the CAS guarantees that only one instance can
  commit a concurrent update
- `UserResolver` is injected by `router_a2a.go`; it takes `*models.User` from the ctx and returns `Username`, which is
  used on Get to verify task ownership (preventing cross-tenant reads of someone else's task)
- Nothing is persisted to MySQL: once the TTL expires the task disappears from Redis. The UI path can still find the
  corresponding message in the `assistant_message` table (an A2A client gets `task_not_found`)
- **`tasks/list` is not implemented**: the A2A specification allows returning `UnsupportedOperation`, and actively
  enumerating tasks across users is meaningless for a built-in assistant and would leak other users' activity

## 7. MCP

P1 registers a single tool wrapping the built-in assistant:

```jsonc
// mcp.Tool
{
  "name": "n9e_assistant",
  "description": "Operate the Nightingale platform via natural language. Returns the assistant's final response as text.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "message":  { "type": "string", "description": "User request or question for the n9e assistant." },
      "chat_id":  { "type": "string", "description": "Optional existing chat ID; when omitted a new chat is created." }
    },
    "required": ["message"]
  }
}
```

The output structure:

```jsonc
// mcpOutput
{
  "content": "...final assistant text...",
  "chat_id": "uuid",
  "seq_id":  3
}
```

Implementation notes:
- `mcp.NewStreamableHTTPHandler` runs with `Stateless: true` — a new server instance is created per request and no
  MCP session state is relied upon, which fits n9e's multi-instance deployment naturally
- Internally the tool goes through `EnsureAssistantChat` + `StartAssistantMessage` and then drains only the stream
  messages with `P=="content"`, returning the final text; reason and step frames are not returned to the MCP caller
  (natural language in, natural language out)

P2 will consider exposing the query tools from `aiagent/builtin_tools.go` individually.

## 8. A2A specification coverage

| Item | Status |
|---|---|
| Executor interface (`Execute`/`Cancel`) | ✅ |
| Streaming events (artifact / status update) | ✅ |
| Heartbeat (working sent after 30 s idle) | ✅ |
| Cancel genuinely interrupts (cancel ctx + mark + finish stream) | ✅ |
| AgentCard SecuritySchemes (X-User-Token) | ✅ |
| TaskStore persistence (`tasks/get` / `tasks/resubscribe`) | ✅ — Redis implementation, Lua CAS safe across instances, 24 h TTL |
| `tasks/list` | ❌ Deliberately not implemented; returns `UnsupportedOperation` per the specification |
| Push Notifications | ⏳ (on demand) |

## 9. Risks

1. **Long idle heartbeat**: a single n9e ReAct round may run for over ten minutes, so the executor sends an empty
   `TaskStateWorking` status update after 30 s of stream idleness to work around the default 60 s idle timeout of
   nginx / ALB.
2. **Write deadline**: `http.Server.WriteTimeout` (40 s by default) also cuts the stream. The `streamingDeadline`
   middleware clears it centrally, which benefits both A2A SSE and long MCP responses.
3. **ChatLock conflicts**: on concurrent requests with the same `ContextID`, `StartAssistantMessage` returns 409 and
   the executor propagates it as an ordinary error.
4. **Risk of TaskID drifting away from the chat**: Cancel goes through `Task.Metadata` rather than "the latest seq in
   the chat", avoiding the race between a `cancel` and an immediately following `message:send` (the old strategy could
   kill a task that had just started).
6. **First release**: the release notes state explicitly that the `/a2a/*` and `/mcp/*` endpoints are enabled by
   default (though authenticated), so enterprise users can set `Disable = true` if they need to.

## 10. Client examples

The repository ships `cmd/a2a-cli`, a command-line test tool built on the official a2a-go SDK:

```bash
# Streaming chat
go run ./cmd/a2a-cli \
    --server http://127.0.0.1:17000 \
    --token  <X-User-Token> \
    --message "Show the alert events currently firing in the prod business group"

# Continue the same chat
go run ./cmd/a2a-cli \
    --server http://127.0.0.1:17000 \
    --token <token> \
    --context-id <chat-id> \
    --message "Analyze the first one in more detail"

# After it finishes, use tasks/get to verify the TaskStore survives across connections
go run ./cmd/a2a-cli --server http://127.0.0.1:17000 --token <t> --message hi --get
```

Plain curl works too. Note that the REST binding path is `/a2a/message:send` (without `/v1`), that `messageId`,
`role`, and `parts` are all required, and that the enum value for `role` is `ROLE_USER`:

```bash
# 1) discover
curl https://n9e.example.com/.well-known/agent-card.json

# 2) send a message (non-streaming)
curl -X POST https://n9e.example.com/a2a/message:send \
  -H "Content-Type: application/json" \
  -H "X-User-Token: <user_token>" \
  -d '{
    "message": {
      "messageId": "req-0001",
      "role": "ROLE_USER",
      "parts": [{ "text": "Show the alert events currently firing in the prod business group" }]
    },
    "metadata": { "lang": "en_US" }
  }'

# 3) continue the same chat (multi-turn): contextId goes inside message
curl -X POST https://n9e.example.com/a2a/message:send \
  -H "Content-Type: application/json" \
  -H "X-User-Token: <user_token>" \
  -d '{
    "message": {
      "messageId": "req-0002",
      "role": "ROLE_USER",
      "contextId": "chat-xxx",
      "parts": [{ "text": "Analyze the first one in more detail" }]
    }
  }'
```
